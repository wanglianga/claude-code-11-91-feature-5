# 充电预约演示系统（Vue 3 + FastAPI + PostgreSQL）

司机按「站点 + 时间窗 + 停留时长 + 最低功率」预约充电，运营方维护枪口并评估对既有预约的影响。
系统同时支持两种预约粒度，并以同一套容量数据给出可核验结论：

- **固定枪口（CONNECTOR）**：确认时锁定一支兼容枪口，位置承诺直观；枪口故障时需迁移订单。
- **资源池（POOL）**：只承诺一个满足插头/功率/无障碍条件的站点名额，到站再分配枪口；
  以「池内同时可履约的枪口数」限制订单，绝不会因为两支枪各自「空闲」就把同一份容量卖两次。

在预约不到空档时，司机还可登记**候补请求**（车辆接口、最低功率、所需时长、到站期限、
可接受替代站点）。预约取消只释放未开始时段，系统按站点规则向合格候补发放
**带截止时刻的一次性邀请**；邀请不是预约，接受并通过容量校验后才确认，
接受 / 超时 / 拒绝 / 人工保留全程留痕，并发接受同一空档只有一笔能确认。

## 二、一键启动（Docker，推荐）

前置：本机已安装 Docker 与 Docker Compose。

```bash
docker compose up --build
```

启动后：

| 服务 | 地址 |
| --- | --- |
| 前端（司机端/运营端两个页签） | http://localhost:8080 |
| 后端 API | http://localhost:8000 |
| Swagger UI（接口文档） | http://localhost:8000/docs |
| PostgreSQL | localhost:5432，库/用户/密码均为 `ccdev` |

后端容器启动时会自动建表，并**仅在空库时**灌入样例数据；重复重启不会清空已有数据。
候补一次性邀请的有效时长由环境变量 `WAITLIST_INVITE_TTL_SECONDS` 控制（默认 120 秒），
演示超时时可临时改小，例如：

```bash
WAITLIST_INVITE_TTL_SECONDS=5 docker compose up --build
```

需要恢复初始演示数据时：

```bash
docker compose exec backend python -m app.seed
```

停止并清理数据卷：

```bash
docker compose down -v
```

## 三、本地开发启动（不使用 Docker）

容器内已预装 Python 3.12 / Node 22 / PostgreSQL 18，下面的命令也适用于普通开发机
（自行准备一个可连接的 PostgreSQL 即可）。

### 1. 后端

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# 指向你的 PostgreSQL，默认 postgresql+psycopg://ccdev:ccdev@127.0.0.1:5432/ccdev
export DATABASE_URL="postgresql+psycopg://用户:密码@主机:5432/库名"
.venv/bin/python -m app.seed           # 重置并灌入样例数据
.venv/bin/uvicorn app.main:app --reload --port 8000
```

### 2. 前端

```bash
cd frontend
npm install
npm run dev      # http://localhost:8080，/api 已代理到 127.0.0.1:8000
```

cd backend

既有 20 项覆盖：候选与限制原因、搜索不产生订单、两种粒度的并发争抢、成功/失败两类
幂等回放、18:10 降额的真实交集判定、整晚订单的部分受影响、取消释放、迟到、池模式到站
分配、充电会话保护、客服替代枪口/费用调整快照、恢复不改写历史、无障碍约束。

候补 17 项覆盖：

- **两条公平规则**：FIFO 下先登记的宽松 Q2 拿走 120kW 枪 E、严格 Q1 在 60kW 枪 F 上无
  合格时段；兼容优先下 Q1 得 E、Q2 得 F，两人都能接单；
- **硬约束**：接口不兼容、功率不足、空档盖不住完整时长、晚于到站期限一律不发邀请；
- **邀请≠预约**：发邀请不产生订单，接受并通过容量校验后才生成 `CONFIRMED` 预约；
- **并发互斥**：两名司机并发接受同一邀请，结果为 `200 + 409`，全局仅一笔确认；
- **超时与迟到接受**：越过截止时刻的接受返回 409、巡检把邀请置 `EXPIRED`，
  绝不写成成功确认，且无任何新预约；
- **拒绝/再次拒绝、人工保留、撤销候补、可接受替代站点、只释放未开始时段**。

### 2. 题面场景 E2E：31 项检查全部通过

先重置数据，再启动后端（用短 TTL 让超时段真实执行），然后：

```bash
cd backend
.venv/bin/python -m app.seed
WAITLIST_INVITE_TTL_SECONDS=5 .venv/bin/uvicorn app.main:app --port 8000 &
PY=.venv/bin/python bash e2e_check.sh
# 结果：通过 31 项，失败 0 项
```

脚本第 9–13 组用真实 HTTP 请求验证候补题面：

9. **FIFO**：取消 E 枪预约后首个邀请发给先登记的 Q2（锁定 120kW 的 E）；再取消 F 枪，
   Q1 因 F 只有 60kW 而收不到邀请，仍是 `QUEUED`；
10. **兼容优先**：切规则后重置，E 枪空档先发给只有 E 能满足的 Q1，F 枪空档再发给 Q2，
    两名司机都拿到合格邀请；
11. **并发接受**：两个并发 `accept` 命中同一邀请，结果码集合恰为 `200,409`，
    全局只有一笔 `WAITLIST_INVITE` 来源的确认预约，邀请最终为 `ACCEPTED`；
12. **拒绝与人工保留**：拒绝后邀请 `DECLINED` 且候补仍排队；人工保留使待响应邀请
    `SUPERSEDED`，对其再接受返回 409；
13. **超时与迟到接受**（短 TTL 实跑）：巡检把过截止时刻的邀请置 `EXPIRED`，
    迟到的接受返回 409、不产生任何成交预约。

## 六、关键设计与约束的落实

- **候选搜索不构成订单**：`POST /api/search` 为纯只读；真正占用容量只发生在确认事务里。
- **事务内重算 + 并发安全**：确认先取站点级 `pg_advisory_xact_lock`，
  在同一事务内重新计算所有重叠切片后落单；并发请求被串行化，同一份能力不可能卖两次。
- **池容量不重复售卖**：每个时间切片统计「合格且未锁定的枪数 − 在途池预约数」，
  全程取最小值作为可确认名额。
- **幂等**：每个写操作携带 `idempotency_key`；首次请求（含 409 业务失败）的响应码与
  响应体被持久化，重复提交原样返回，同键不同参数返回 409。
- **状态机**：`CONFIRMED → ARRIVED → CHARGING → COMPLETED`，
  以及 `CANCELLED / NO_SHOW`（释放容量）、`NEEDS_RESELECTION / MANUAL_CONTACT`
  （维护影响）；非法转换返回 409。池模式在「到站」时才分配具体枪口。
- **维护按真实交集判定**：维护窗口与预约按半开区间求交集，交集为空则完全不影响；
  整晚订单遇到中途降额时，已履约区间与待履约区间在原因中分别说明。
  仍满足车辆需求的订单继续履约，不满足的进入改选/人工联系。
- **充电会话保护**：`CHARGING` 订单不能被取消、不能被客服替代枪口流程迁移，
  维护只会给出 `PROTECTED_CHARGING` 判定。
- **历史不可改写**：确认时写入承诺快照（枪号/功率/池名额），之后降额、恢复、
  迁移都不会修改它；客服动作固化当时的订单状态与原枪/目标枪设备快照；
  设备恢复只结束维护窗口并追加 `DEVICE_RECOVERED` 事件，不自动回滚订单状态。

### 候补（waitlist）专项约束

- **只释放未开始时段**：取消/失约时以 `max(当前时刻, 预约开始)` 为空档起点，
  已经开始的部分不会被再次发放；固定枪口释放 1 支枪、资源池释放 1 个名额，每轮最多 1 个邀请。
- **两条规则、同一硬门槛**：FIFO 严格按 `created_at, id`；兼容优先按「站点内能满足该候补的
  枪口数」升序（越稀缺越优先）、同等候选再按登记时间。两者都只向**接口/无障碍/功率能力匹配、
  空档能完整覆盖所需时长、开始时刻不晚于到站期限、站点在可接受范围内**的请求发邀请。
- **邀请是一次性的、且不是预约**：邀请带 `expires_at` 截止时刻；接受在站点级咨询锁内
  重新做容量校验，通过才生成 `CONFIRMED` 预约并把邀请置 `ACCEPTED`，全程同一事务。
- **并发接受互斥**：接受与确认共用站点级咨询锁，两名司机并发接受同一空档必然串行，
  先到者确认，后到者收到 409，数据库中只可能有一笔成交预约。
- **超时与迟到接受不算成功**：越过截止时刻的接受返回 409 且不写订单；
  `POST /api/waitlist/sweep` 巡检把超时邀请置 `EXPIRED`、把超到站期限的候补置 `CLOSED`。
  业务失败遵循幂等框架「无部分写入、可原样重放」的约定。
- **拒绝/再拒绝与人工保留全部留痕**：拒绝（`DECLINED`）、超时（`EXPIRED`）后候补保持
  原登记顺位回到开放队列，可再次收邀请；人工保留/撤销候补把待响应邀请置 `SUPERSEDED`；
  每个候补都有独立事件流（`WAITLIST_JOINED / INVITE_ISSUED / INVITE_ACCEPTED /
  INVITE_DECLINED / INVITE_EXPIRED / INVITE_MANUAL_HOLD / WAITLIST_CANCELLED / WAITLIST_CLOSED`）。
